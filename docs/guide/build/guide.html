Chapter 0: How to use this guide

What this guide is

A study guide for one project: a benchmark of Arabic sentiment analysis, built from an empty folder to a deployed API. Every chapter explains what was done, why, what else was possible, how it was implemented, what broke, and what the numbers say. It is written for the author to study from, not as a tutorial for strangers.

Two kinds of statements appear throughout, and the guide keeps them apart:

  • Measured here: numbers and behaviors produced by our own runs (for example, “TF-IDF scored 0.9411 on HARD”).
  • General knowledge: claims about other datasets, models or tools that were not run in this project. These are marked, and anything not checked is flagged as unverified.

If a sentence in a chapter says “I did not test this”, take it literally.

Chapter template

Each chapter uses the same sections:

  1. What: the step, in a few lines.
  2. Why: the decision and the evidence behind it.
  3. Alternatives: what else was possible and why it lost.
  4. How: the core code, explained piece by piece. Boilerplate stays in the repo.
  5. What went wrong: real bugs and detours.
  6. Numbers: results from our runs.
  7. Check yourself: questions an interviewer could ask.

Glossary

Term Meaning in this project
Macro-F1 Mean of the F1 score of each class. With two classes, it weighs negative and positive equally, so ignoring the minority class is punished.
MSA Modern Standard Arabic, the formal written variety.
Dialect Regional spoken and informal written varieties (Egyptian, Jordanian, Gulf and others).
Encoder A BERT-style transformer that turns text into vectors. Here fine-tuned with a classification head.
Fine-tuning Continuing training of a pretrained model on a labeled task.
Few-shot Giving an LLM a handful of labeled examples in the prompt, without training.
TF-IDF A text representation that weights terms by how rare they are across documents.
Bootstrap CI A confidence interval from resampling test predictions with replacement (1,000 or 500 resamples here).
Seed The random number generator setting. Different seeds give slightly different trained models.
Leakage Information in the input that gives away the label, or the same example appearing in train and test.
Descriptor The leading Booking.com score label in HARD reviews (Chapter 5).
VRAM GPU memory. 8 GB on this laptop, about 6.5 GiB usable.
bf16 A 16-bit number format with the range of 32-bit floats, used for training.
Invalid rate Share of LLM replies that were not a usable label. Counted as errors.

How to read the numbers

  • Macro-F1 values are on a 0 to 1 scale.
  • ASTD (242 test rows) and AJGT (180) are small. A bootstrap interval there is about plus or minus 4 to 5 points, so smaller gaps are noise.
  • HARD and LABR encoder runs are single seed, and the LLM comparison on those two uses 300-row samples. Those 300-row numbers are not comparable with full-test numbers.
  • “Tuned” XLM-R means one fixed alternative configuration, not a search.

Chapter 1: Objective and plan

What

Build a benchmark of Arabic sentiment analysis across Modern Standard Arabic and dialects, then turn the best model into a deployed service. The project is a portfolio piece for ML Engineer and AI Engineering roles at UAE employers, so it has to show both research discipline (fair comparisons, honest limits) and engineering (tracking, tests, containers, deployment).

The original brief

These were the requirements at the start, in the author’s words condensed:

  • Datasets: LABR, HARD, ASTD, AJGT.
  • Models: fine-tuned encoders (AraBERT, MARBERT, XLM-R) versus a few-shot Arabic-capable LLM (Jais or similar).
  • A TF-IDF + logistic regression baseline, a results table, and an error analysis focused on dialect failures.
  • A FastAPI service, containerized with Docker, and deployed.
  • Experiment tracking with MLflow or Weights & Biases.
  • A clean GitHub repo with about 12 meaningful commits and a strong README.
  • Constraints: a Lenovo LOQ laptop (RTX 5070, 8 GB VRAM, 32 GB RAM, Windows 11 with WSL2), free Kaggle and Colab GPUs as overflow, 3 to 4 weeks.

Why this project

Why sentiment analysis? It is a small, well-understood task, so the effort goes into method (data quality, evaluation, comparison) and not into task definition. Labels exist in public datasets, and the problem is simple enough for one laptop.

Why Arabic with dialects? Arabic is a strong fit for UAE employers, and dialect variation is a real engineering problem: one language, many written varieties, and spelling that is not standardized. A benchmark that covers both MSA and dialect is more informative than one that covers either alone.

Why a benchmark, and not a single model? A single model with a good score says little. The value is in the comparison: what does a fine-tuned encoder buy over TF-IDF, and how does a prompted LLM compare? And in the discipline around it: same rows, same splits, uncertainty reported.

Why serve and deploy it? Employers for ML engineering roles want to see a model leave the notebook. Serving, containerizing, testing and deploying show that.

Alternatives to this project framing

Alternative Why it lost
One model, one dataset, one score Easy, but nothing to defend and nothing to learn from
3-class sentiment (adding neutral) Cleaner for real use, but AJGT has no neutral class and 3-star reviews are ambiguous, so scores would not be comparable across datasets
A larger, newer LLM-only study Cheaper to run, but free API caps limit test size, and it skips fine-tuning, which the roles value
Training from scratch Pointless at this data size; pretrained models do far better
Many datasets (10 or more) Dilutes the analysis. Four datasets already span two domains and several dialects

Whether better datasets or models exist is covered where they matter, in Chapters 3 and 8.

The plan

Week Focus Deliverable
1 Data and baseline Four datasets in one schema, fixed splits, TF-IDF baseline logged
2 Encoder fine-tuning AraBERT, MARBERT, XLM-R on all datasets, first full results table
3 LLM few-shot and error analysis LLM runs, dialect analysis, error write-up
4 Serving and polish FastAPI, Docker, deployment, README with honest limitations

Principles that governed every step:

  1. Same rows for every system. Differences between models must come from the models, not from the data they saw.
  2. Validation picks, test judges. Epochs, prompts and configurations are chosen on the validation split, and test is scored once per final model.
  3. Report uncertainty. Bootstrap intervals, several seeds where test sets are tiny.
  4. Report what failed. Leaks, bugs and weak results go in the write-up.
  5. Decide before looking. Where a choice could be tuned toward a good-looking result (the prompt language, the tuned XLM-R configuration), the rule was fixed in advance.

What actually happened versus the plan

  • Jais was replaced by ALLaM. Jais 13B does not fit on the laptop, and the Kaggle route needed custom model code and 4-bit loading that I could not verify would work. ALLaM, an Arabic-specialist model, was available on the Groq API, so it filled the same role with much less risk. The Kaggle option was dropped.
  • Two extra LLMs. Qwen and gpt-oss ran alongside ALLaM, giving a general-purpose comparison.
  • The LLM phase took days, not hours. Free-tier caps of 200,000 tokens per day per model turned a one-evening job into several days of resumed runs (Chapter 11).
  • A data leak changed the evaluation. HARD’s leading score label inflated every score, so HARD became two benchmark variants (Chapter 5).
  • Deployment moved clouds. Hugging Face Docker Spaces were not selectable on a free account, so the service runs on Azure Container Apps (Chapter 18).
  • Commit count. The repo has more than the planned 12 commits, because the project grew.

What success looks like

Not “highest score”, but:

  • Every number can be reproduced from the repo.
  • Every comparison is on identical rows and every gap is judged against its noise.
  • Every limitation is written down.
  • The deployed service works, is tested, and is protected by a key.

Chapter 2: Environment

What

Set up a reproducible GPU development environment on a Windows laptop: WSL2 with Ubuntu 24.04, the NVIDIA driver on the Windows side, a CUDA-enabled PyTorch build managed by uv, and a git repository on GitHub.

Machine: Lenovo LOQ 15IRX10 (i7-13650HX, RTX 5070 Laptop GPU with 8 GB, 32 GB RAM, 1 TB SSD), Windows 11.

Why

Why WSL2 and not native Windows? The machine runs Windows, but nearly all ML tooling (shell scripts, Docker, uv, package builds) assumes Linux. WSL2 runs a real Linux kernel, and CUDA reaches the GPU through the Windows driver, so the same GPU is usable from Linux with no dual boot.

Why the driver goes on Windows only. Inside WSL you must not install an NVIDIA driver. WSL2 uses the Windows driver, and nvidia-smi inside Ubuntu reports it. You also do not need the CUDA toolkit: the PyTorch wheel bundles the CUDA runtime it needs.

Why a new PyTorch build was mandatory. The RTX 5070 is Blackwell (compute capability sm_120). An older PyTorch wheel can detect the GPU and then crash on the first real computation with “no kernel image is available”. The wheel must be built for CUDA 12.8 or newer.

Why uv and not conda. - uv.lock records exact versions of every package, so the environment can be rebuilt identically. - Installs are fast. - The same lock-and-sync flow maps onto a Docker build. - The project is pure Python plus PyTorch wheels, so conda’s strength (non-Python native dependencies) was not needed.

Why work in the Linux filesystem. Files under /mnt/c or /mnt/d cross a translation layer between Windows and Linux that is slow for many small reads (tokenization, dataset loading, package installs). The project lives in ~/projects, on the Linux side. GitHub is the backup.

Alternatives

Option Verdict
Native Windows with PyTorch Possible. I did not test it. Shell scripts, Docker workflows and some tools are more awkward, and the Dockerfile later targets Linux anyway
Dual boot Linux Full speed and no translation layer, but costs a reboot per switch. Overkill for this project
Conda or Miniconda Works. Would have meant no lockfile by default and slower resolves. Better when you need non-Python native libraries
pip with venv Works, but no lockfile and no dependency resolver comparable to uv
Poetry Has a lockfile too. uv was chosen for speed and simplicity. I did not compare them in this project
Colab or Kaggle only Free GPUs, but sessions are time-limited and not reproducible across runs. Kept only as overflow for anything over 8 GB, which in the end was not needed

How

1. WSL2 and Ubuntu (Windows, PowerShell as Administrator)

wsl --install -d Ubuntu-24.04
wsl --update
nvidia-smi
wsl --status

The Windows NVIDIA driver must be recent. nvidia-smi on Windows must show the RTX 5070 before anything else is attempted.

2. Cap WSL resources with .wslconfig

A file named exactly .wslconfig (dot, no extension) in C:\Users\<name>\:

[wsl2]
memory=22GB
processors=14
swap=8GB
  • memory=22GB leaves about 10 GB to Windows. WSL2 by default takes a share of Windows RAM (I recall half, so 16 GB here, not verified), and Docker Desktop later uses the same allowance.
  • processors=14 matches the CPU’s logical processors (the i7-13650HX has 20 threads, so 14 leaves headroom for Windows).
  • swap=8GB is overflow when memory runs short.

Apply with wsl --shutdown, wait 10 seconds, reopen Ubuntu, then check:

free -h
nproc

Expected: about 21 GiB total memory, 8 GiB swap, 14 processors. (free shows slightly less than 22 GB because of overhead.)

3. Inside Ubuntu

sudo apt update && sudo apt install -y build-essential git curl
nvidia-smi

nvidia-smi must list the RTX 5070 here. If it does not, the fix is on the Windows driver side.

4. uv and the project

curl -LsSf https://astral.sh/uv/install.sh | sh
source ~/.bashrc
mkdir -p ~/projects && cd ~/projects
uv init arabic-sentiment-benchmark --python 3.12
cd arabic-sentiment-benchmark
uv add torch --index pytorch=https://download.pytorch.org/whl/cu128
uv add transformers datasets accelerate evaluate scikit-learn pandas numpy mlflow
uv add --dev ruff pytest jupyter

The install command for uv downloads Astral’s official script and runs it. -LsSf means follow redirects, stay silent, still show errors, and fail on HTTP errors. uv installs into ~/.local/bin with no sudo and does not touch the system Python. Version in this project: uv 0.13.1.

[tool.uv.sources]

[[tool.uv.index]]
name = "pytorch"

[dependency-groups]
dev = ["jupyter>=1.1.1", "pytest>=9.1.1", "ruff>=0.17.1"]

Line by line: - dependencies: runtime packages with minimum versions. Exact versions live in uv.lock, which is the file that makes the environment reproducible. - [build-system] and [tool.hatch...]: makes src/arabic_sentiment an installable package, so python -m arabic_sentiment.data and from arabic_sentiment.baseline import ... work from anywhere in the project. - [tool.uv.sources] plus [[tool.uv.index]]: tells uv to fetch torch from PyTorch’s CUDA 12.8 index and not from PyPI (the PyPI wheel may not match the GPU). - [dependency-groups] dev: tools that are not needed to run the code (lint, tests, notebooks).

Known weakness: requests (used by llm_eval.py) and huggingface_hub (used by several scripts) are imported directly but not declared. They arrive as dependencies of other packages, so they work today, but a future version of those packages could drop them. The fix is uv add requests huggingface-hub.

6. The CUDA check

uv run python -c "import torch; print(torch.__version__, torch.version.cuda); print(torch.cuda.is_available(), torch.cuda.get_device_name(0)); print(torch.cuda.get_arch_list()); x=torch.randn(4096,4096,device='cuda',dtype=torch.bfloat16); print((x@x).float().mean().item()); print(torch.cuda.mem_get_info())"

What each part proves:

Part Proves
torch.__version__, torch.version.cuda The wheel is a CUDA build and which version
torch.cuda.is_available() The driver is visible. This alone is not enough
torch.cuda.get_arch_list() The wheel contains kernels for this GPU. sm_120 must appear
torch.randn(4096,4096, device='cuda', dtype=torch.bfloat16) then x @ x Compiled kernels actually run on this GPU in bf16, the format used for training
.float().mean().item() Brings one number back to the CPU, proving the result is readable
torch.cuda.mem_get_info() Free and total VRAM in bytes
